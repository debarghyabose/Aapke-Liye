What happens to one voice note

Process flowchart

The core is a loop: listen, extract, check what is missing, ask, repeat until the claim is complete, then read it back for confirmation.

flowchart TD
  A([Victim speaks in app]) --> B[Member 2 sends audio + session_id]
  B --> C[Preprocess: ffmpeg to 16 kHz mono WAV, trim silence]
  C --> D{Language known?}
  D -- No --> E[Language ID: Whisper detect / Bhashini ALD]
  D -- Yes --> F
  E --> F[Speech to text: Bhashini ASR, Whisper as fallback]
  F --> G{ASR confidence OK?}
  G -- No --> H[Ask user to repeat, in their language]
  H --> A
  G -- Yes --> I[Normalize: numbers, amounts, place names]
  I --> J[LLM extraction with JSON schema + previous claim state]
  J --> K[Validate with Pydantic, merge into claim]
  K --> L{Required fields missing?}
  L -- Yes --> M[Pick most important missing field]
  M --> N[LLM writes one follow-up question in user's language]
  N --> O[Member 4 shows / speaks question]
  O --> A
  L -- No --> P[Generate readback summary in user's language]
  P --> Q{User confirms?}
  Q -- Corrects something --> A
  Q -- Yes --> R[Final claim JSON, status = complete]
  R --> S[Member 2 stores claim]
  S --> T[[Phase 2: insurance claims, ID reissue, escalation letters]]

LayerPick
Speech to textBhashini ASR for Hindi, Bengali, Marathi, Telugu, Tamil. Whisper large-v3 for English and as fallback.
Language IDWhisper detect_language, or let the UI send the user's chosen language.
Claim LLMAny LLM with JSON-schema or tool-calling output (for example claude-sonnet-5-5; claude-haiku-5-5 for cheaper turns).
ValidationPydantic models, one per schema.
ServiceFastAPI + Uvicorn, Docker image.
Design rule. Let the LLM extract, but decide "what is missing" with plain code. A fixed list of required fields per loss type is predictable, testable, and never hallucinates a field as filled. Use the LLM only to phrase the question kindly in the user's language.
Do these in order

Build steps

Tick each step as you finish it. Ticks are saved in this browser only.

0 of 12 done
  1. Phase 1 · Day 1

    Agree the contracts with Member 2 and Member 4

    • Share the claim JSON schema and the API request/response shapes (see Data contracts).
    • Agree audio format (WAV or OGG/Opus), max length (30–60 s), and how session_id is passed.
    • Agree language codes: en hi bn mr te ta.

    All three of you have signed off on one schema file in the repo.

  2. Phase 1

    Set up the service skeleton

    • FastAPI app with /health, /v1/transcribe, /v1/claim/turn.
    • Return hard-coded mock responses first so Member 2 and Member 4 can integrate immediately.
    • Put API keys in .env, never in git.

    Member 2 can call your mock endpoints from their backend.

  3. Phase 1

    Speech to text in 6 languages

    • Preprocess with ffmpeg: 16 kHz, mono, 16-bit WAV; trim leading/trailing silence.
    • Write an ASRAdapter interface with BhashiniASR and WhisperASR implementations.
    • Register on the Bhashini (ULCA) portal for a user ID and API key; use the pipeline config call to get the ASR service per language.
    • Fallback: if Bhashini errors or times out (>8 s), use Whisper.
    • Return transcript, language, and a confidence score.

    One sample clip per language comes back as readable text.

  4. Phase 1

    Normalize the transcript

    • Convert spoken amounts to numbers: "do lakh" → 200000, "pachas hazaar" → 50000, "₹1.5 lakh" → 150000.
    • Keep the original transcript too; store both.
    • Optional: translate to English with Bhashini NMT so the LLM prompt is simpler. Test with and without.

    Unit tests pass for lakh/crore/hazaar in all 6 languages.

  5. Phase 1

    Claim extraction with the LLM

    • Send the transcript plus the current claim state; ask for an updated claim that matches the JSON schema (tool calling or structured output).
    • Instruct: never guess; leave a field null if it was not said. Return a per-field confidence.
    • Validate with Pydantic; on failure, retry once with the error message.
    • Merge: new non-null values overwrite old ones only when confidence is higher.

    A Hindi clip like "Mera naam Ramesh hai, Puri mein ghar toot gaya, do lakh ka nuksaan" fills name, location, loss type and amount.

  6. Phase 1

    Missing fields and follow-up question

    • Required list in code: name, phone, district, state, disaster type, incident date, at least one loss with type and amount.
    • Extra required fields per loss type: crop → crop name + area (acres); livestock → animal + count; house → kutcha/pucca + damage level.
    • Ask about one field at a time, most important first.
    • LLM writes the question in the user's language, short and gentle. Optional TTS so it can be spoken aloud.
    • When nothing is missing, generate a readback summary and ask for confirmation.

    A full conversation in Hindi reaches status: complete in 3–5 turns.

  7. Phase 1

    Test set and evaluation

    • Record 3 scenarios × 6 languages = 18 clips minimum (house, crop, livestock). Add background noise to a few.
    • Write the expected claim JSON for each clip by hand (the "golden" answer).
    • Script eval.py that reports field accuracy and missing-field detection per language.

    Every language scores at least 80% field accuracy, or you know why it doesn't.

  8. Phase 1 · Demo

    Integrate and rehearse the demo

    • Replace mocks with the real pipeline; run end to end through Member 2's backend and Member 4's screen.
    • Pick your two strongest languages for the live demo; keep pre-recorded clips as backup.
    • Log latency per stage; target under 6 s per turn.

    Live demo works three times in a row.

  9. Phase 2

    Before/after damage comparison

    • Input: baseline photo and damage photo. Send both to a vision model with a fixed rubric.
    • Output: damage_score 0–100, level (none / partial / severe / destroyed), visible damaged items, and a short reason.
    • Flag low-confidence or mismatched photos (different building) for human review instead of scoring.

    10 test photo pairs score in the right level band.

  10. Phase 2

    Replacement applications (Aadhaar, ration card, land records)

    • One drafter function: draft(doc_type, claim, template) → filled letter.
    • Fill only fields present in the claim; mark gaps as [TO FILL] for the user.

    Each of the 3 request types drafts correctly from one test claim.

  11. Phase 2

    Insurance claims (home, vehicle, crop)

    • Reuse the same drafter; add per-insurance required fields (policy number, vehicle registration, PMFBY crop details).
    • Run the missing-field checker before drafting so the bot can ask for policy numbers.

    A crop claim draft includes crop, area, season, loss estimate and damage photos.

  12. Phase 2

    Auto-escalation letters (follow-ups, grievances, RTI)

    • Trigger from Member 2 when a claim has been stuck past N days.
    • Use Member 5's templates only; the LLM fills facts (claim ID, dates, office) and never invents legal wording.
    • Escalation ladder: reminder → grievance → RTI application.

    Member 5 reviews three generated letters and approves them.

Data contracts

The claim object is what everyone builds around. Version it (schema_version) so changes don't break Member 2 and Member 4.

Claim JSON

{
  "schema_version": "1.0",
  "session_id": "s_8f21",
  "language": "hi",
  "status": "incomplete",
  "claimant": {
    "name": "Ramesh Kumar",
    "phone": null
  },
  "location": {
    "village": "Satapada",
    "district": "Puri",
    "state": "Odisha",
    "pincode": null
  },
  "disaster_type": "cyclone",
  "incident_date": "2026-11-12",
  "losses": [
    {
      "type": "house",
      "description": "roof collapsed",
      "house_kind": "kutcha",
      "damage_level": "severe",
      "amount_inr": 200000
    }
  ],
  "documents_lost": ["ration_card"],
  "field_confidence": { "claimant.name": 0.95 },
  "transcripts": [
    { "original": "...", "english": "..." }
  ]

POST /v1/claim/turn

// request (from Member 2)
{
  "session_id": "s_8f21",
  "language": "hi",          // optional
  "audio_url": "https://...", // or base64
  "claim": { ... }           // current state
}

// response
{
  "claim": { ... },          // updated
  "transcript": "...",
  "missing_fields": ["claimant.phone"],
  "next_question": {
    "field": "claimant.phone",
    "text": "आपका फ़ोन नंबर क्या है?",
    "text_en": "What is your phone number?",
    "audio_url": null        // if TTS on
  },
  "status": "incomplete"     // or
                             // "needs_confirmation",
                             // "complete"
}
